# The engine and platform programme: acceptance ledger

This folder records how far the programme in
[`../ENGINE-AND-PLATFORM-BRIEF.md`](../ENGINE-AND-PLATFORM-BRIEF.md) (version 2)
has been delivered. It is measured against the brief's own acceptance rules,
not against effort spent.

| file | what it is |
| --- | --- |
| [`acceptance-ledger.json`](acceptance-ledger.json) | Every acceptance unit, with its source, gate, weight, status, release state and evidence. This is the source file. |
| [`LEDGER.md`](LEDGER.md) | The same, rendered with the completion figures. Generated by `node scripts/programme-ledger.mjs`; do not edit it by hand. |
| [`FINDINGS.md`](FINDINGS.md) | Defects and unsupported claims found by the audits, ranked by severity, each with its disposition. |
| [`STATUS.md`](STATUS.md) | The current checkpoint: identities, gates run, blockers, and the next task. |

`scripts/programme-ledger.test.mjs` holds these files to the rules below.

## Where the units come from

The authority is version 2 of the brief. Where version 2 cites a version 1
rule ("v1 1a's rule", "v1 M2.6", "version 1's §5"), that rule applies. Version
1 is in [`../evidence/engine-audit-2026-09-22/BRIEF-v1.md`](../evidence/engine-audit-2026-09-22/BRIEF-v1.md).
Owner decisions recorded in the repository also apply. Every requirement in
Phases 0–4, Tracks A, S and G, the five bets' first slices (§4.1, sequenced by
§4.5) and the start of the conventions registry (§4.4) is an acceptance unit.
Large requirements are split into units that pass or fail on their own, such
as one unit per house system or one per event class.

Items the brief itself places later are listed under "Not in the denominator",
each with the passage that says so:

- differentiators "alongside or after the bets" (§4.2);
- reach items (§4.3);
- the "Deferred, with reasons" list;
- "Not in Phase 2";
- demand-gated consumer tools (§4.6).

Moving an item into or out of the denominator needs a recorded decision. The
§9 measures (downloads, calls, citations, search and assistant reach) are
outcomes, tracked separately. Finishing the engineering is not the same as
reaching the goal of being the default endpoint for astrology computation.

Version 1's M3 time rules that version 2 does not renumber are units too:
leap seconds, UT1−UTC, band propagation, receipt time scale, and the time-5
flag probes. Version 2's time axis names them as the goal.

## Weights

Each unit's weight is an estimate in working days. It comes from the brief's
own effort figures, divided among the phase's units:

| part | brief's estimate | weight here |
| --- | --- | ---: |
| Phase 0 | 1–2 days | 2.5 |
| Phase 1, with v1 M3's remaining time rules | about 2 weeks | 14.5 |
| Phase 2 | about 8 weeks | 47.6 |
| Phase 3 | about 4 weeks | 24.5 |
| Phase 4 | 6–7 weeks | 30.5 |
| Tracks A, S, G | "all phases" | 20.35 |
| Bets B1–B5, first slices | two weeks or less each | 41.0 |
| §4.4 registry start | — | 1.5 |
| **Total, 151 units** | | **182.45** |

The weights were fixed on 2026-09-28, before any unit's status was assigned.
The JSON records a digest of every (id, weight) pair. Changing an id or a
weight changes the digest, and the test fails until a dated entry under
`denominator.changes` records the reason and the decision.

## Status and release

A unit counts toward completion only when it is **accepted**. That means two
things: the gate's evidence is committed and reproducible, and the unit is in
the release state its gate needs. For an engine capability, that state is an
engine candidate the site vendors and production serves. Publication to a
registry is a unit of its own (P3.1a).

The other states record progress without counting it. They are kept apart so
that implemented, merged, deployed and published never blur:

| status | meaning |
| --- | --- |
| `validated` | The gate's evidence exists, but the release state or a ratification is still missing. |
| `merged` | The code is on main, and the gate is not yet evidenced. |
| `implemented` | The code exists in an open pull request or a prototype. |
| `partial` | Some of the unit exists. |
| `failed` | The gate was measured and failed. The verdict stays recorded, as §8 requires. |
| `not-started` | Nothing yet. |

A unit whose next step needs an owner or outside action carries `blockedBy`,
naming the action. Blocked weight stays in the denominator and is reported
separately. It is never counted as done and never dropped.

A gate that passes only under an amendment adopted after its residual was seen
counts as `validated`, not `accepted`, until the owner ratifies the amendment.
This applies to amendments A1 and A3 in the preregistration record.

## Updating

1. Change a unit's status, release or evidence in `acceptance-ledger.json` and
   cite the evidence (a committed path, a commit, a deployment).
2. Run `node scripts/programme-ledger.mjs` to regenerate `LEDGER.md`, and
   update `STATUS.md` with the figure it prints.
3. `npx vitest run scripts/programme-ledger.test.mjs` must pass.
